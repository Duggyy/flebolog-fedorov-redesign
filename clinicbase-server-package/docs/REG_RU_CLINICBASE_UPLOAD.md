# Загрузка ClinicBase на reg.ru

## Что получилось

ClinicBase теперь состоит из двух частей:

- фронтенд: файлы из `dist-clinicbase`, которые открываются в браузере на `clinicbase.ru`;
- серверная база: PHP API в папке `api` и MySQL-таблицы из `database/clinicbase.mysql.sql`.

На обычном хостинге reg.ru Node.js не нужен. React-сайт работает как статические файлы, PHP отвечает за логин и сохранение данных в MySQL.

## 1. Создать базу MySQL

1. Откройте ispmanager.
2. Перейдите в раздел `Базы данных`.
3. Нажмите `Создать`.
4. Создайте базу, например:
   - имя базы: `u3452052_clinicbase`
   - пользователь: `u3452052_clinicbase`
   - пароль: придумайте сложный пароль и сохраните его.
5. Откройте `phpMyAdmin`.
6. Выберите созданную базу.
7. Откройте вкладку `Импорт`.
8. Загрузите файл `database/clinicbase.mysql.sql`.
9. Нажмите `Вперед`.

После импорта появятся таблицы:

- `doctors`
- `patients`
- `visits`
- `field_suggestions` (устаревшее хранение подсказок, оставлено для переноса)
- `dictionary_entries` (справочники: краткое имя, полный текст, цвет, подпункты)

## 2. Загрузить файлы сайта

> **Главное правило: не удаляйте папку `api` целиком.**
> В ней лежит `api/config.php` — пароль от базы. В архиве этого файла нет и быть
> не должно, поэтому «удалить старые файлы и распаковать заново» стирает его
> вместе со всеми данными доступа. Программа после этого не пускает внутрь:
> API отвечает «сервер не настроен», а на экране входа появляется «Сервер не
> готов — на сервере нет api/config.php». Выглядит как поломка базы, хотя база
> цела. Так и случилось 23.10.2026.

1. Откройте `Менеджер файлов` в ispmanager.
2. Перейдите в папку сайта:
   `/www/clinicbase.ru`
3. Убедитесь, что `api/config.php` на месте. Если он есть — **ничего не удаляйте**,
   просто распакуйте архив с заменой файлов: `config.php` в архиве отсутствует,
   поэтому распаковка его не тронет.
4. Если `config.php` всё-таки пропал — восстановите его из своей копии или
   создайте заново по образцу `api/config.sample.php` (см. раздел 3).
5. Загрузите архив `clinicbase-upload.zip` в `/www/clinicbase.ru`.
6. Распакуйте архив прямо в `/www/clinicbase.ru`.
7. Сразу после распаковки выполните живую проверку — она скажет, всё ли на месте:
   `npm run check:live` (подробности в разделе 6).

В корне `/www/clinicbase.ru` должны лежать:

- `index.html`
- `.htaccess`
- папка `assets`
- папка `api` (внутри — `index.php`, `config.php` и `config.sample.php`)
- папка `data` (внутри — `dictionary-template.json`)
- `favicon.svg`
- `favicon-preview.png`
- `robots.txt`

Важно: файлы не должны оказаться во вложенной папке вроде `/www/clinicbase.ru/dist-clinicbase/index.html`. `index.html` должен лежать прямо в `/www/clinicbase.ru`.

## 3. Настроить подключение к базе

1. В `/www/clinicbase.ru/api` найдите файл `config.sample.php`.
2. Скопируйте его в этой же папке.
3. Новую копию назовите `config.php`.
4. Откройте `config.php` на редактирование.
5. Заполните данные MySQL:

```php
<?php

return [
    'db_host' => 'localhost',
    'db_name' => 'u3452052_clinicbase',
    'db_user' => 'u3452052_clinicbase',
    'db_password' => 'ВАШ_ПАРОЛЬ_ОТ_MYSQL',
    'admin_login' => 'admin',
    'admin_password' => 'ВАШ_НОВЫЙ_ПАРОЛЬ_АДМИНА',
];
```

`admin_password` обязательно замените. Не оставляйте `CHANGE_THIS_PASSWORD`.

## 4. Проверить API

Откройте в браузере:

`https://clinicbase.ru/api/index.php?action=session`

Если все настроено правильно, должен появиться JSON-ответ:

```json
{"session":null}
```

Если видите `server_not_configured`, значит нет файла `api/config.php`.

Если видите `database_connection_failed`, значит ошибка в имени базы, пользователе или пароле MySQL.

## 5. Войти в систему

Откройте:

`https://clinicbase.ru/login`

Админ:

- логин: значение `admin_login` из `api/config.php`
- пароль: значение `admin_password` из `api/config.php`

После входа админ попадает в админку и может создавать врачей.

Тестовые врачи из SQL:

- `fedorov / 1234`
- `ivanova / 1234`

После проверки лучше зайти в админку, открыть каждого тестового врача и назначить новый пароль.

## 6. Что загружать при следующих обновлениях

При обновлении интерфейса обычно нужно:

1. Собрать проект командой `npm run build:clinicbase`.
2. Создать новый `clinicbase-upload.zip`.
3. Загрузить и распаковать архив в `/www/clinicbase.ru`, **не удаляя папку `api`**:
   в ней `config.php` с паролем от базы, и в архиве его нет.
4. Сразу выполнить живую проверку — `npm run check:live` (раздел 6а).

SQL-файл импортируется только при первом создании базы. Повторный импорт может создать ошибку `table already exists`.

## 6а. Проверка после выкладки: `npm run check:live`

Преддеплойная проверка (`npm run check:deploy`) смотрит локальную папку сборки и о
сервере ничего не знает. А ломается выкладка именно на сервере, и тихо: страница
открывается, вход не работает. Поэтому после каждой загрузки:

```
npm run check:live
```

Скрипт обращается к `https://clinicbase.ru` и печатает по строке на каждый пункт:

| Что проверяет | Как выглядит поломка |
|---|---|
| сайт отдаётся | `сайт не отдаётся — HTTP 500` |
| бандл загружается | `бандл не загружается` |
| сборка на сервере та же, что локально | `на сервере ДРУГАЯ сборка` — архив не распаковался или распаковался не туда |
| `data/dictionary-template.json` на месте | `шаблон не разбирается как JSON` |
| PHP работает | `api/index.php отдаёт HTML вместо JSON` |
| `api/config.php` существует | `на сервере нет api/config.php` — восстановите файл (раздел 3) |
| база доступна | `API не подключается к базе` — проверьте `db_name`, `db_user`, `db_password` |

Если все строки `OK` и в конце `ИТОГ: сервер в порядке` — можно показывать врачу.
Код возврата 1 означает, что есть проблемы: их разбор в строках `ОШИБКА`.

С логином и паролем проверка идёт глубже — смотрит то, что видно только изнутри:
читаются ли пациенты и справочники. Без этого отсутствие таблицы не заметно:

```
npm run check:live -- --login fedorov --password 1234
```

Флаг `--probe-width` добавляет ещё один пункт — не обрезается ли длинный текст записи.
Он записывает пробную строку в справочники, читает её обратно и сразу удаляет:

```
npm run check:live -- --login fedorov --password 1234 --probe-width
```

Флаг `--probe-save` проверяет то, что не видно при чтении: **сохраняется ли приём**.
Он отправляет серверу ровно те данные, которые тот только что отдал, — ничего не меняется:

```
npm run check:live -- --login fedorov --password 1234 --probe-save
```

Это важно, потому что чтение и запись ломаются по отдельности. 25.10.2026 чтение
работало, а сохранение падало: в таблице `visits` не было столбца `record_time`,
и сервер отвечал `Unknown column 'record_time'`. Экран при этом заполнялся, и
поломка была видна только по кнопке «Сохранить». Проверка называет недостающий
столбец прямым текстом.

Так проверяют третий шаг миграций (раздел 7): пока колонка `VARCHAR(500)`,
в строке будет `ОШИБКА текст записи обрезается — записано 650 знаков, прочитано 500`.
Это единственный способ увидеть обрезку снаружи: сама программа о ней молчит,
потому что сервер отвечает «ok».

Ещё один пункт с логином — знает ли сервер новые поля приёма из шаблона ИБ:

```
OK    новые поля приёма сервер знает — 6 полей из шаблона ИБ
```

Если вместо этого `ОШИБКА сервер не знает новые поля приёма — нет: appealReason, ...`,
значит на хостинге остался старый `api/index.php`: выгрузите архив заново. Поля при
этом выглядят рабочими, врач их заполняет, а сохранить нечего — они просто не уходят
на сервер.

## 7. Если база уже создана — применить миграции

`database/clinicbase.mysql.sql` создаёт базу с нуля. На уже работающую базу он не подействует:
`CREATE TABLE` не меняет существующие таблицы. Поэтому изменения схемы лежат отдельными
файлами в `database/migrations/`, и их надо применять
по одному через phpMyAdmin (вкладка `SQL` → вставить содержимое файла → `Вперед`).

Эти файлы лежат в папке пакета на компьютере — в архиве `clinicbase-upload.zip` их нет,
архив везёт только файлы сайта. Для миграций ничего загружать на сервер не нужно:
файл открывается локально, его текст вставляется в phpMyAdmin.

| Файл | Что добавляет | Состояние на 25.10.2026 |
|---|---|---|
| `2026-10-22-visits-record-time.sql` | колонку `record_time` в `visits`. Без неё **не сохраняется приём**: сервер отвечает `Unknown column 'record_time'`, а программа пишет «сохранено локально». Чтение при этом работает, поэтому поломка видна только по кнопке «Сохранить» | применена 25.10.2026 |
| `2026-10-23-dictionary-entries.sql` | таблицу `dictionary_entries`, перенос старых подсказок и починку уникальности `field_suggestions` | применена частично: таблица есть, шаги с проверками через `information_schema` не прошли |
| `2026-10-23-dictionary-short-text-long.sql` | снимает предел 500 знаков у текста записи — иначе длинные назначения из шаблона обрежутся | применена |
| `2026-10-25-visits-ib-fields.sql` | шесть колонок в `visits` под поля из шаблона ИБ: `appeal_reason`, `appeal_case`, `diagnosis_classification`, `operation_type`, `clinical_data`, `dressing`. Без них **не сохраняется приём** — сервер отвечает `Unknown column 'appeal_reason'` | **применить** |

Порядок важен — сначала `record_time`, потом справочники, потом длину текста,
последним поля из шаблона ИБ. Повторный запуск: у первого и последнего файла даст
`#1060 Duplicate column name` (значит «уже есть»), у третьего — ничего не сделает,
второй заново запускать не нужно (см. ниже).

**`database/apply-dictionaries.sql` — исторический файл.** Это те же два шага справочников
одним куском, он применялся 23.10.2026 и своё дело сделал. Заново запускать его не нужно
и не получится: внутри есть проверки через служебную базу `information_schema`, а у
пользователя MySQL на этом хостинге на неё нет прав — импорт упадёт с
`#1044 Access denied ... to database 'information_schema'`. Для оставшегося шага
(длина текста) есть отдельный маленький файл, в нём таких проверок нет.

Как применять (phpMyAdmin):

1. В левом списке **выберите базу** `u3452052_clinicbase`. Если её там нет —
   phpMyAdmin открыт под другим пользователем MySQL: зайдите в него из ispmanager
   (кнопка у самой базы), а не по общему адресу.
2. Вкладка **SQL** → вставьте текст файла → **Вперёд**.
   (Вкладка **Импорт** тоже годится: «Выберите файл» → **Вперёд**.)
3. Убедитесь, что слева есть таблица `dictionary_entries`.
4. Проверьте снаружи: `npm run check:live -- --login <логин> --password <пароль>` —
   должно быть `OK справочники читаются — N записей`.

Если пропустить второй файл, программа откроется, но экран «Справочники» будет пустым:
API вернёт ошибку на запрос `dictionaries`. Если пропустить третий — шаблон загрузится,
но у трёх самых длинных назначений пропадёт хвост.

### Как понять, что третий шаг прошёл

Файл заканчивается запросом `SHOW COLUMNS FROM dictionary_entries LIKE 'short_text'`,
и phpMyAdmin показывает его результат — одну строку с колонками `Field`, `Type`, `Null`,
`Key`, `Default`, `Extra`:

| `Type` в результате | Что значит |
|---|---|
| `varchar(2000)` | готово, шаг выполнен |
| `varchar(500)` | **не выполнилось**, выше есть текст ошибки — пришлите его скриншотом |

Если строк нет вовсе — значит запросы ушли не в ту базу: вернитесь к пункту 1.

### Про ошибку `#1044 Access denied ... information_schema`

Первый вариант третьего шага сам проверял формат строки таблицы и текущую ширину
колонки — через служебную базу `information_schema`. На этом хостинге у пользователя
MySQL прав на неё нет, поэтому импорт падал на первом же таком запросе. Вывод, который
стоит запомнить: **в миграциях для этого хостинга нельзя обращаться к
`information_schema`** — только `SHOW`, `ALTER`, `CREATE`, `INSERT` в пределах своей базы.

### Про ошибку `#1215 Cannot add foreign key constraint`

Она уже случалась 23.10.2026, когда третий шаг был написан как «сделать колонку `TEXT`».
Причина: смена типа на `TEXT` перестраивает таблицу целиком, а при перестройке MySQL
заново создаёт внешний ключ `dictionary_entries.doctor_id → doctors.id`. Удлинение
`VARCHAR(500) → VARCHAR(2000)` делается на месте, без перестройки, и ключа не касается —
поэтому в файле теперь `VARCHAR`.

Если ошибка повторится, разбираться нужно по её тексту: `#1118 Row size too large`
значит, что формат строки на этой базе старый (`COMPACT`) и 2000 знаков в неё не влезают —
тогда в файле надо заменить `VARCHAR(2000)` на `VARCHAR(1000)`: 1000 знаков покрывают
шаблон с запасом (самое длинное назначение — 650). Любую другую ошибку присылайте
скриншотом — по номеру видно причину.

## 7а. Загрузить шаблон истории болезни

В архиве пакета лежит `data/dictionary-template.json` — справочник, собранный из
`Шаблон ИБ 2026_10.docx` (560 записей в 26 разделах). Отдельно загружать его не нужно:
он уезжает вместе с файлами сайта.

В программе: меню **«Справочники» → «Загрузить шаблон ИБ»**. Появится окно с числом
записей, после подтверждения они встанут в «Общие». Если что-то не так — там же
**«Отменить загрузку шаблона»**: вернёт состояние, которое было до загрузки, и в браузере,
и на сервере.

Загрузка заменяет «Общие» целиком. Личные записи врача не трогаются.

### Подпункты: дефис в начале строки

Часть строк в шаблоне начинается с дефиса — так размечены подпункты:

```
Состояние после
-флебэктомии
-ЭВЛК
```

В панели у такой подсказки стоит плюс: подпункты раскрываются по нему и
показываются уже без дефиса. Щелчок по подсказке вставляет её текст, щелчок по
подпункту дописывает его следом — так и набирается «Состояние после флебэктомии».

Дефис — только разметка, в текст поля он не попадает. В редакторе справочника
строка правится как есть, вместе с дефисом. Если дефис стоит в начале раздела и
подсказки над ним нет («Наследственность…», «Клинические данные»), строка
остаётся обычной подсказкой — плюса у неё не будет, раскрывать нечего.

**Если шаблон уже загружался раньше (530 записей).** 25.10.2026 в форме появились поля
под шесть разделов, которым раньше некуда было лечь: «Повод обращения», «Случай обращения»,
«Классификация диагноза», «Вид операции», «Клинические данные», «Перевязка». Их 30 записей
теперь входят в шаблон — 560 вместо 530. Чтобы они появились, загрузите шаблон ещё раз:
старые общие записи заменятся новыми, личные останутся. Порядок важен: сначала миграция
`2026-10-25-visits-ib-fields.sql` (раздел 7), потом выгрузка архива, иначе новые поля
не сохранятся.

## 8. Важное по безопасности

- Включите SSL-сертификат для `clinicbase.ru`.
- Работайте через `https://clinicbase.ru`, не через `http`.
- Поставьте сложный пароль администратора.
- Регулярно делайте резервные копии MySQL-базы в ispmanager.
- Не пересылайте `api/config.php` посторонним: в нем пароль от базы.
